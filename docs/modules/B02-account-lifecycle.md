# B02 — account-lifecycle

**Tier:** Backend
**Code location:** `services/api/app/accounts/`
**Milestone:** 1 (migration), 6 (deletion)
**Status:** not started

## Purpose

The two flows that move or destroy a user's entire data footprint: upgrading a
guest into a permanent account without losing their first lesson, and deleting an
account so completely that it satisfies app-store review and privacy law. Split
from `B01` because both touch every table and both are unrecoverable when wrong.

## Scope

**Owns**
- Guest → account migration: anonymous auth upgraded in place, all data
  re-attached
- Account deletion: full purge across every table plus external systems
- The ordering guarantees both flows need

**Does not own**
- Token verification and provisioning → `B01`
- The soft account gate UI → `C06`
- Client-side pending queues that must flush post-migration → `E05`, `C04`

## Data touched

Every table that carries a `user_id`, plus `user` itself. Also PostHog identity
(`F06`) and FCM tokens (`B19`).

## Migration

Firebase anonymous auth is upgraded in place, so the UID is preserved and most
rows need no rewrite. The flow must still: confirm the upgrade succeeded before
flushing any client queue, re-link analytics identity so pre-signup events stay
attached, and be idempotent — a retried migration cannot duplicate progress.

The stake is explicit in the source: the user has just completed a full lesson as
a guest and is being asked to create an account *in order to keep it*
(`FEATURE_PLAN.md:36-37`). Losing it at that exact moment is the worst possible
failure in the product.

## Deletion

Must purge, not soft-delete: `user`, `enrollment`, `progress`, `exercise_result`,
`review_item`, `daily_activity`, `tutor_thread`, `tutor_message`, FCM tokens, and
analytics identity. Shared `course` rows are **not** deleted — they belong to the
cache in `B10`, not to the user — but any private course does go.

## Decisions inherited

- **Anonymous auth upgraded to a permanent account, preserving first-lesson
  progress** (`ARCHITECTURE.md:57-59`).
- **Deletion must actually purge user data** — it matters for app-store review and
  privacy law (`FEATURE_PLAN.md:153`).
- **Store the minimum PII needed** (`FEATURE_PLAN.md:182`), which keeps the purge
  surface small.

## Open questions

- Whether deletion is synchronous or queued; queued is safer at volume but needs a
  guaranteed-completion story for compliance.
- Whether a private course generated by a deleted user can be promoted to the
  shared cache instead of destroyed, and whether that is defensible.
- Grace period before purge, if any.

## Acceptance criteria

- [ ] A guest who completes a lesson and then signs up retains every card,
      exercise result, and XP point
- [ ] Migration is idempotent under retry
- [ ] Analytics identity survives the transition as one person
- [ ] Deletion leaves no row anywhere carrying the deleted `user_id`, verified by
      a query across all tables
- [ ] Deletion removes FCM tokens so no notification can reach a deleted user
- [ ] Shared cached courses survive the deletion of a user who generated them
